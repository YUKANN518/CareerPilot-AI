# CareerPilot AI Phase 2 Core Flow Audit

Audited on 2026-09-16 before Phase 2 business-code changes.

## Scope and current flow

```text
Resume upload
→ PDF/DOCX text blocks
→ AI-compatible resume structuring
→ verbatim evidence validation
→ user review and confirmation
→ immutable ResumeVersion + confirmed ResumeSkill evidence
→ deterministic JobRequirementExtractor
→ six-dimension deterministic matching
→ optional FAISS semantic relevance
→ deterministic blocking policy
→ stored MatchReport, details and evidence
```

The default UI uses `deterministic-v1.1` or `hybrid-v1`. `hybrid-v1` uses the same
`deterministic-v1.1` result plus semantic relevance.

## 1. How each matching dimension is calculated

The six dimensions and their real configured weights are:

| Dimension | Weight | Current calculation |
| --- | ---: | --- |
| Hard skills | 35% | Canonical skill equality after deterministic dictionary/alias normalization. Required skills have weight 2, preferred skills weight 1. Confirmed evidence = 100%, present but unconfirmed/incomplete = 50%, missing = 0%, unknown dictionary term = 70%. |
| Evidence strength | 20% | Required/preferred weighted evidence quality. It considers evidence count, source locator, project/work section, keyword overlap and multiple skills in one section. It is not a simple evidence-coverage ratio. |
| Experience and education | 15% | Average of two deterministic sub-scores. Experience uses non-overlapping dated work intervals; education uses an ordered degree rank. Project dates are not counted as formal work experience. |
| Language, location and eligibility | 10% | Deterministic language containment, location compatibility and explicit user-profile work eligibility. Unknown candidate data receives neutral 70% rather than being treated as failure. |
| User preferences | 10% | Compares configured locations, employment types, target roles, salary and industries. No configured preferences means no score penalty. |
| Other conditions | 10% | Currently certificate requirements and their explicit required/preferred markers. |

`rule_score` is the sum of the six weighted contributions. Thresholds for the deterministic
recommendation are fixed in code: 85, 70, 55 and 40, with risk severity and completeness caps
applied before the recommendation is returned.

## 2. Deterministic versus semantic scores

All six dimensions above are deterministic. `hybrid-v1` separately computes semantic relevance
from local resume/job chunks using an embedding provider and FAISS. Only compatible section pairs
are searched. Similarities below the configured threshold are discarded, the top K evidence pairs
are retained, and their normalized similarity scores are averaged.

The real hybrid formula is:

```text
final hybrid score = deterministic rule score × 70%
                   + semantic relevance score × 30%
```

Semantic similarity does not mark a skill as matched. Skill status is determined only by canonical
skill matching plus confirmed resume evidence. A blocking risk or recommendation cap survives a
high semantic score.

## 3. Where LLMs are used

- Resume parsing may use an OpenAI-compatible provider to produce structured fields.
- Every extracted skill evidence quote is checked as a whitespace-normalized verbatim substring
  of the extracted resume text before it can be saved.
- The user must review the parsed profile. Matching accepts only a confirmed `ResumeVersion`.
- Job-requirement extraction, skill normalization, scoring, blocking, recommendation and semantic
  combination do not call an LLM.
- Match Report explanation is currently generated by application code from stored results; there
  is no LLM explanation step capable of changing a score, skill or risk.

Therefore the current design already follows: LLM structures input; deterministic code decides
hard outcomes.

## 4. Existing evidence and traceability

The report already stores:

- immutable `resume_version_id`;
- a scoring-config snapshot including weights, rule versions, semantic settings and embedding
  metadata;
- a structured `job_requirements_snapshot`;
- skill status arrays, risks, recommendation and dimension scores;
- `MatchDetail` rows for skills, dimensions, risks, conditions, report policy and semantic output;
- `MatchEvidence` rows with resume quote, resume skill, source locator, page/paragraph, job quote,
  source field, matching rule and confidence;
- semantic evidence pairs with both resume text and job text.

The skill conclusion can already be traced from report → detail → evidence → confirmed resume
version and job requirement. Report calculations do not change when the live resume or job is
subsequently viewed.

## 5. Current explanation gaps

1. `DimensionScore` contains score, weight, contribution and a generic explanation, but has no
   explicit evidence keys or gap codes. The current dimension drawer usually opens empty because
   dimension details do not own evidence rows.
2. `ResumeSkill.evidence_section` is saved as `technical_skills` or `soft_skills`, even when the
   quote came from a project, work experience or education block. Page/paragraph provenance is
   retained, but the human-facing source category is too coarse.
3. Matched-skill cards show an evidence count but not the quote and source inline.
4. Missing-skill cards do not show the job requirement and “no verified evidence” reason inline.
5. All risks are returned through the historically named `hard_requirement_risks` field. Required
   skill gaps, informational unknowns, preference mismatches and true blocking conflicts are mixed.
6. Risks have severity but no explicit classification (`SKILL_GAP` versus `BLOCKING_RISK`) or
   verification state (`UNVERIFIED` versus `CONFLICT`).
7. The report has an evidence-strength score but no lightweight count of verified, partially
   supported and missing skill requirements.
8. The report UI fetches the current Job to display title/company. The calculation snapshot and
   report result are stable, but that heading can reflect later job edits.
9. Job required/preferred typing is explicit for skills. Experience, education, language,
   certificate and work eligibility have availability and explicit/preferred flags, but the report
   does not present them as one readable structured requirement summary.
10. The UI exposes the stored weights but lacks one concise public “How this score was calculated”
    explanation connecting deterministic rules, semantic relevance and blocking precedence.

## 6. Blocking Risk generation

Blocking is deterministic and versioned by `blocking-policy-v1`:

- known work-eligibility conflict with an explicit job rule;
- explicit mandatory language mismatch;
- explicit mandatory certificate absence/mismatch;
- explicit non-substitutable education shortfall;
- explicit experience minimum with a gap of at least three years.

Unknown candidate facts currently create INFO risks rather than confirmed conflicts. The
recommendation becomes `NOT_RECOMMENDED` only for a true `BLOCKING` severity. A high semantic score
can change the numeric hybrid score but cannot remove this conclusion.

The missing presentation concept is an explicit status: an unknown mandatory fact should be shown
as `UNVERIFIED`, while a known contradiction should be shown as `CONFLICT`.

## 7. Skill Gap generation

Job skills come from stored `JobSkill` rows, structured raw-data skill lists and dictionary-backed
mentions in the requirements text. Required and preferred are retained. Resume skills are indexed
through a versioned canonical dictionary.

- `MATCHED`: equivalent skill plus user-confirmed non-empty evidence.
- `PARTIAL`: skill record exists but confirmation or evidence is incomplete.
- `MISSING`: no equivalent skill record.
- `UNKNOWN`: job term is outside the known dictionary.

A non-matched required skill also produces a risk for prioritization, but it remains a skill gap;
it is not a blocking qualification conflict.

## 8. Input verification and failures

- Unconfirmed resume versions are rejected with `RESUME_VERSION_NOT_CONFIRMED`.
- A confirmed version with no confirmed skill evidence is rejected with
  `RESUME_SKILL_EVIDENCE_REQUIRED`.
- Missing/foreign resume and job inputs are rejected before scoring.
- A semantic/index failure fails the semantic workflow node and the run; no fake semantic score is
  generated.
- Job information completeness and unknown criteria cap confidence/recommendation rather than
  pretending missing job data is satisfied.
- Match processing and Match Report already render loading, not-found, forbidden and operation
  errors, but the final report needs a clearer domain empty state for evidence/gaps.

## 9. Snapshot and reproducibility finding

`ResumeVersion` is immutable in the product flow and the report stores all result arrays, evidence,
algorithm configuration and extracted job requirements. This makes the computed result
reproducible for the stored artifacts.

There is no complete original Job snapshot. A later job edit does not recalculate an old report,
but the report heading currently reads the live title/company and the original description is not
fully recoverable from the report. Phase 2 can add a low-risk JSON input snapshot to existing report
metadata without a new database table. Deleting a resume intentionally cascades its reports, so
long-term report retention after source deletion is not currently supported.

## 10. Phase 2 implementation direction

Without changing weights or adding a business module:

- extend the existing explanation structures rather than replace them;
- classify risk type and verification state without changing risk severity/score behavior;
- bind dimension explanations to stored evidence keys and gap codes;
- expose a non-scoring evidence-coverage summary;
- preserve a lightweight resume/job input snapshot in existing report metadata;
- improve evidence source categories during future resume confirmation, while mapping old values
  in the UI for compatibility;
- separate Matched Skills, Skill Gaps and Blocking Risks in the report;
- add a truthful methodology disclosure based on the stored scoring snapshot;
- add focused backend/frontend/E2E regression tests.

No matching weights should change in Phase 2.
